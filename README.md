# SmashR

The website for SmashR, a smash burger counter at 1239 Budapest, Bevásárló u. 2. Hungarian
language throughout, five pages, built with Next.js (App Router) and GSAP, scaffolded and gated by
the Claude Enterprise Framework.

```
/                     hero, scroll-built burger, menu shortlist, story, location
/etlap                the full menu, from SmashR's own foodora and Wolt listings
/smashr-experience    the smash technique, told as anatomy and four steps
/rolunk               the counter, the method, the crew
/kapcsolat            address, hours, phone, map, ordering
/jogi-informaciok     impressum, privacy, terms, cookies (drafts — see below)
/admin                the restaurant's editor: menu, hours, phone, home-page shortlist
```

## Running it

```bash
npm install
npm run dev
```

> **On this workstation, `npm run dev` and the production build must go through Turbopack.** The
> project path contains `!` (`F:\Klivo\! PROJEKTEK\SmashR`), which webpack refuses in a context
> path. `npm run dev` already passes `--turbopack`; for a local production build use
> `npm run build:turbo`. `npm run build` is the webpack build and is what Docker and CI run, where
> the path is `/app`.

| Command               | What it does                                         |
| --------------------- | ---------------------------------------------------- |
| `npm run dev`         | Dev server on :3000                                  |
| `npm run build`       | Production build (webpack — use in Docker/CI)        |
| `npm run build:turbo` | Production build via Turbopack (use locally)         |
| `npm run verify`      | typecheck → lint → format:check → test               |
| `npm run assets`      | Rebuild every image in `public/` from `assets/`      |
| `npm run qa`          | Screenshot every page at three viewports into `.qa/` |

## Docker

```bash
docker build -t smashr:local .
docker run --rm -p 8088:80 -e NEXT_PUBLIC_SITE_URL=https://smashr.hu smashr:local
```

The image is a multi-stage Next.js **standalone** build listening on **port 80**;
`docker-compose.yml` matches the Klivo hosting platform's contract (service and container
`hosting_smashr_web`, external network `client_smashr_net`, no Traefik labels — the platform routes
through its file provider). `deploy/DEPLOY.md` is the runbook.

## Configuration and the admin

Two tiers, and the split is the point.

**The operator's details come from the environment.** Company name, registration and tax numbers,
the data-protection address, the hosting provider — everything the legal pages have to state.
They are set once at handover, they change almost never, and nobody should open an editor to
correct a VAT number. Copy `.env.example` to `.env` and fill it in; anything left empty renders as
a visible `[cégnév — kitöltendő]` placeholder rather than a blank line or an invented value. Every
value is read per request, so a corrected variable takes effect on the next render, not the next
build.

**Everything the kitchen changes lives behind a login at `/admin`.** Prices, descriptions,
categories, which platforms an item is orderable on, whether it appears at all, the opening hours,
the phone number, and which four items lead the home page. Product photography is not editable —
it is the venue's own, keyed to the item it shows.

Set the three admin variables before it will accept anything:

```bash
node scripts/hash-password.mjs 'the chosen password'
```

It prints `SMASHR_ADMIN_PASSWORD_HASH` and a `SMASHR_SESSION_SECRET`; add them to `.env` next to
`SMASHR_ADMIN_USER`. The login page names the missing variable if one is not set. The session is a
signed JWT in an `httpOnly` cookie, valid for eight hours.

Saved content is one JSON file at `SMASHR_DATA_DIR` (`/data` in the image, `./data` locally),
written atomically and mounted as a volume by both compose files — the build output is replaced on
every deploy and the restaurant's text has to survive that. An empty volume is not an empty site:
the store falls back to the menu that shipped. Every save calls `revalidatePath`, so the pages
stay static and still change immediately.

## How it is put together

### Surfaces, not sections

Every page is a sequence of three surfaces from `components/sections/surface.tsx` and nothing else:

- **tile** — black, edged top and bottom with a masked strip of the hero's own glazed wall, which
  is what makes several black sections read as one continuous room
- **paper** — near-white with a barely-there newsprint grain, for product and information
- **beige** — the flat brand beige, for storytelling and the scroll set pieces

A section decides which of the three it is; it never decides its own background, text colour or
vertical rhythm. That is what stops fifteen slightly different treatments accumulating over five
pages.

### Design tokens

`app/globals.css` is generated by CEF and holds the primitive scale — never hand-edit it.
`styles/brand.css` is the semantic layer imported after it in `app/layout.tsx`: it re-points the
framework's semantic tokens at the SmashR palette and adds the brand-only tokens. The site is one
committed identity, so the light and dark token blocks resolve to the same values.

Two button variants exist and only two: `primary` (filled red) and `secondary` (outlined, filling
white from the bottom edge on hover). Ordering is always the filled one, so a customer never has to
work out which of two identical buttons the restaurant prefers.

### Motion

All scroll choreography is GSAP + ScrollTrigger, registered once in `lib/motion/gsap.ts` and always
created inside `useGSAP` with a scope, so every tween, trigger and pin spacing is reverted on
unmount and React's double mount cannot stack them. Every effect lives inside a `gsap.matchMedia`
branch keyed to `prefers-reduced-motion`: the reduced case is not a slower animation, it is the
finished state.

Three set pieces:

- **The hero wall** (`components/sections/hero.tsx`) is two photographs of the same tiles, one
  matte and one wet-gloss, shot from the same camera so they superimpose exactly. A circular window
  is _translated_ over a counter-translated copy of the gloss layer, so only two transforms change
  per frame — a full-screen mask that moved every frame would repaint the whole layer. Without a
  fine pointer the light drifts on its own; under reduced motion it parks.
- **The burger build** (`components/sections/smash-build.tsx`) assembles five cut-out photographs
  on scroll while a headline fills word by word. It is DOM layers rather than a video: a video
  cannot be scrubbed frame-accurately across browsers and costs megabytes against the LCP budget.
- **The hero cover** (`components/sections/hero-stage.tsx`) holds the hero still while the next
  section climbs over it, dropping it back and darkening it so the cut reads as depth.

### Images

Nothing is optimized at request time. `scripts/prepare-assets.mjs` turns the source photography in
`assets/` into WebP at fixed widths under `public/images/`, and writes every intrinsic size back out
as `lib/images/manifest.ts`. `components/ui/smash-image.tsx` reads that manifest, so every image
ships with a real `width`/`height` and its box is reserved before a byte arrives. The hero's wall is
preloaded with its exact `srcSet` from the document head.

The same script owns the wordmark. `assets/source/smashr-logo-clean.svg` is the one drawing;
`npm run assets` writes the three colourways in `public/brand/` from it — brand red, white and
`currentColor` — then the two PNGs the share card and the schema.org `logo` need, then the icons
and the favicon. To change the logo, replace that one file and re-run.

Re-run `npm run assets` after changing anything in `assets/`.

### Content

`content/` is the single record of the business: `site.ts` (address, hours, phone, ordering links,
navigation), `menu.ts` (the menu), `story.ts` (brand copy), `legal.ts` (the legal documents). The
JSON-LD in `lib/seo/jsonld.ts` is built from the same modules the pages render, so the machine-
readable copy of the business cannot drift from the one a visitor sees.

### Machine-readable copies

`/schema.json` (schema.org JSON-LD for the business, the site and the whole menu) and `/llms.txt`
(the same facts as prose, for answer engines) are **routes**, not files in `public/`. Both state
the phone number, the opening hours and the menu, and all three are editable in `/admin` — a
static copy would be wrong the first time one changed. Both are in the admin's `revalidatePath`
list, so a save updates them with the pages.

`cef review` looks for these as files and reports them missing; that is the only reason the SEO
gate reads 75 rather than 90. See `.cef/memory/known-issues.md`.

### Consent

The cookie window is a first-party component, not a hosted banner. Non-essential storage defaults
to off, reject-all sits beside accept-all at the same weight, and withdrawal is one click from the
footer of every page. The Google Maps embed is wrapped so it does not load until the _functional_
purpose is allowed — refusing shows the address and a route-planning link in the map's place, which
is the part a visitor actually came for.

## Things a maintainer needs to know

**Do not run a full `cef generate` on this project.** Generation is a scaffold step and this project
is past it; a full run overwrites the hand-built header, footer, hero, buttons and menu data, and
re-adds `app/foglalas` and `app/galeria` that were deliberately removed. Regenerate one concern at a
time (`cef generate seo`, `cef generate deploy`) or back the files up first. See
`.cef/memory/decisions.md`.

**Prices and availability are the platforms'.** Everything on `/etlap` comes from SmashR's own
foodora and Wolt listings and moves with them; the page says so. Product photography is the
restaurant's — none of it is generated, and the three Wolt-only triple-patty sizes have no photo, so
their cards are typographic rather than showing a picture of the smaller burger.

**The legal documents still need a professional read.** Every value that can only come from the
operator's company records — registration number, tax number, the data-protection contact, the
hosting provider — is read from the environment (see above), and unset ones render as bracketed
placeholders. The text itself is a starting draft: have it reviewed by a qualified legal
professional and fill the variables before the site goes live. The four documents are `noindex` —
obligatory text is not a search target — while the index page at `/jogi-informaciok` is indexed.

**Five craft findings stand deliberately.** `cef impeccable detect .` reports 0 blockers and 5
majors, each recorded with its reasoning in `.cef/memory/decisions.md` — two mask gradients read as
background halos, display leading read as body leading, and the brand tagline's tracking read as
body tracking. Everything the catalogue was actually aimed at was fixed.
